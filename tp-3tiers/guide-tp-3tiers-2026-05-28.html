Installer Docker via Ansible

⏱ 15–20 min ▼
Objectif : Utiliser Ansible pour installer Docker sur l'OVA. C'est Ansible qui gère la configuration du système, pas Terraform.
📋 Rappel clé : Ansible utilise le module apt pour installer des paquets sur Ubuntu/Debian. Le paramètre become: yes est nécessaire pour les opérations root.

Ouvre tp-3tiers/ansible/playbooks/01-install-docker.yml et observe la structure : un play avec become: yes, une tâche apt pour installer les paquets, puis des tâches pour démarrer le service et ajouter l'utilisateur au groupe docker.

💡 À retenir : Le module apt accepte une liste de paquets via name: [pkg1, pkg2]. become: yes est obligatoire pour toute opération système nécessitant des droits root.
⚠ Piège classique : Oublier become: yes pour l'installation de paquets provoque une erreur de permission. Et attention à ne pas démarrer le service avant de l'installer !
📋 Inventaire Ansible : À cette étape, l'inventaire généré par Terraform n'existe pas encore (il sera créé à l'étape 2). On utilise donc l'inventaire statique inventories/hosts.ini fourni dans le scaffold, qui cible simplement localhost. À partir de l'étape 2, l'ansible.cfg basculera automatiquement sur inventories/generated.ini.

Lancer le playbook

cd tp-3tiers/ansible ansible-playbook -i inventories/hosts.ini playbooks/01-install-docker.yml -v -K # -K demande le mot de passe sudo (become: yes dans le playbook) — entrer : 3iac1p

Créer les réseaux Docker avec Terraform

⏱ 15–20 min ▼
Objectif : Créer 3 réseaux Docker via Terraform. Le réseau db_net doit être internal=true pour qu'aucun conteneur dessus ne puisse initier de connexion vers internet.

Ouvre tp-3tiers/terraform/main.tf et observe les 3 blocs docker_network : dmz_net et app_net sont des réseaux standard, db_net a internal = true. Comprends pourquoi chaque réseau a ou n'a pas ce paramètre (→ QCM Q2).

Déployer PostgreSQL (sans port exposé)

⏱ 15–20 min ▼
Objectif : Configurer le conteneur PostgreSQL dans main.tf avec 3 contraintes de sécurité : réseau db_net uniquement, aucun port exposé vers l'hôte, volume persistant monté.

Observe le bloc resource "docker_container" "postgres" dans tp-3tiers/terraform/main.tf : réseau db_net, volume persistant, variables d'environnement, absence de bloc ports {}. Comprends pourquoi chaque choix est fait (→ QCM Q3).

💡 Rappel architecture : Flask peut joindre PostgreSQL via le nom du conteneur (postgres) parce qu'ils sont tous les deux sur db_net. Mais personne de l'extérieur ne doit pouvoir joindre PostgreSQL directement → pas de bloc ports {}.
⚠ Piège classique : Ajouter ports { internal = 5432; external = 5432 } expose la base de données sur le réseau de l'hôte. En production c'est une faille critique.

Variables d'environnement PostgreSQL attendues

POSTGRES_DB ← var.db_name POSTGRES_USER ← var.db_user POSTGRES_PASSWORD ← var.db_password (variable sensitive !)

Appliquer les modifications

terraform apply

Configurer Nginx (sécurité) + Ansible Vault

⏱ 20–25 min ▼
Objectif : Compléter le template Nginx avec les en-têtes de sécurité et le rate limiting. Chiffrer le mot de passe DB avec Ansible Vault.
📋 Note sur flask_app : L'image python:3.11-slim utilisée dans ce TP est une image de base sans application Flask réelle — le conteneur démarre puis s'arrête immédiatement. curl http://localhost/ retourne donc un 502 Bad Gateway (nginx ne trouve pas de backend), ce qui est normal dans le cadre de ce TP. L'important est de vérifier que Nginx répond (code HTTP présent) et que les en-têtes de sécurité sont bien là — ils apparaissent dans la réponse Nginx quelle que soit la réponse du backend.

Partie A — Template Nginx

Ouvre tp-3tiers/ansible/templates/nginx.conf.j2 et observe les éléments de sécurité déjà en place. Pour chaque directive, comprends son rôle (→ QCM Q4) :

# 1. server_tokens off → masque la version Nginx dans les headers HTTP # 2. add_header X-Frame-Options → protection contre le clickjacking # 3. add_header X-Content-Type → empêche le MIME sniffing # 4. add_header X-XSS-Protection → protection XSS (navigateurs anciens) # 5. add_header Referrer-Policy → contrôle les infos envoyées au site cible # 6. limit_req zone=app → rate limiting contre le brute-force/DDoS # 7. proxy_pass flask_app:5000 → nom de conteneur Docker, pas localhost ! # 8. proxy_hide_header X-Powered-By → masque la stack applicative

Partie B — Ansible Vault (comprendre le principe)

📋 Sécurité allégée pour ce TP : Le mot de passe DB est pré-rempli en clair dans group_vars/all.yml pour simplifier l'exécution et la vérification. Le chiffrement Vault est présenté ici comme exercice de compréhension — le playbook fonctionne sans lui. En production, un secret en clair dans un fichier Git est une faille critique.

Ouvre tp-3tiers/ansible/group_vars/all.yml et observe le commentaire sur db_password. La commande suivante est donnée à titre informatif — son exécution est optionnelle pour ce TP :

Vault — syntaxe à retenir (exécution optionnelle)

# Depuis tp-3tiers/ansible/ # 1. Créer le fichier vault password (ne jamais committer) echo "MonMotDePasseVault" > .vault_pass && chmod 600 .vault_pass # 2. Chiffrer — copier la sortie !vault | dans group_vars/all.yml à la place du mot de passe en clair ansible-vault encrypt_string 'MonMotDePasseSecret42' \ --name 'db_password' \ --vault-password-file .vault_pass
💡 Rappel : !vault est le tag YAML qui indique à Ansible que la valeur est chiffrée. Si tu chiffres le mot de passe, ajoute --vault-password-file .vault_pass à la commande ansible-playbook ci-dessous.
📋 Nginx dans Docker, pas sur l'hôte : Le module Ansible template écrit sur le système de fichiers de la machine où Ansible s'exécute (ici l'OVA). Mais nginx tourne dans un conteneur Docker dont le système de fichiers est isolé. Le playbook génère donc la config dans /tmp/ sur l'hôte, puis utilise docker cp pour la transférer dans le conteneur.
⚠️ Répertoire de travail obligatoire : Ansible charge ansible.cfg depuis le répertoire courant. Ce fichier définit l'inventaire et le chemin des group_vars/. Si tu te trouves ailleurs, la variable flask_upstream (définie dans group_vars/all.yml) sera introuvable et le playbook échouera.

Se positionner dans le bon dossier

cd ~/tp-3tiers/ansible

Avant de déployer Nginx, vérifie que le conteneur Flask est bien démarré — c'est lui que Nginx va proxifier :

Vérifier que Flask est en cours d'exécution

docker ps | grep flask_app
flask_app Up X seconds python:3.11-slim … # Si le conteneur n'apparaît pas, relance : terraform apply (depuis tp-3tiers/terraform/)
💡 D'où vient flask_upstream ? La variable est définie dans group_vars/all.yml : grep flask_upstream group_vars/all.yml
flask_upstream: "flask_app:5000"
C'est le nom du conteneur Docker (flask_app) et son port interne (5000). Ansible l'injecte dans le template nginx.conf.j2 via la directive proxy_pass.

Déployer la configuration Nginx

ansible-playbook playbooks/02-configure-nginx.yml -v # Pas de -K ici : ce playbook utilise become: no (docker cp ne nécessite pas sudo)

Annexe — Mettre à jour l'OVA avec le dépôt Git (nouveau TP)

5 min ▼

Quand un nouveau TP est publié ou que le formateur pousse des corrections, l'OVA doit être synchronisée avec le dépôt Git distant. Cette procédure explique comment récupérer les nouveaux fichiers sans perdre ton travail.

📥 Cas 1 — Tu n'as pas modifié les fichiers scaffold (cas habituel)

Si tu as seulement complété les fichiers dans tp-3tiers/ ou créé tes propres fichiers (.tfvars, inventaires générés…), un simple git pull suffit — ces fichiers sont ignorés par .gitignore et ne seront pas touchés.

# Depuis la racine du dépôt cd ~/3iac1-lab-starter # Vérifier l'état avant toute chose git status # Récupérer les mises à jour git pull origin main # Vérifier les nouveaux fichiers reçus git log --oneline -5 ls tp-3tiers/ # le nouveau dossier doit apparaître
💡 Fichiers protégés par .gitignore : terraform.tfvars, .terraform/, inventories/generated.ini, .vault_pass ne sont jamais trackés. Un git pull ne les modifie jamais.

⚠️ Cas 2 — Tu as modifié un fichier scaffold (ex : main.tf, un playbook…)

Si tu as édité des fichiers trackés par Git (les fichiers scaffold fournis), git pull risque de te signaler un conflit. Deux options :

# ── Option A : mettre ton travail de côté temporairement (stash) ── git stash # sauvegarde tes modifications locales git pull origin main # récupère les mises à jour git stash pop # réapplique tes modifications par-dessus # Si conflit : git ouvre un marqueur <<<<<<< — résoudre manuellement, puis : # git add <fichier> && git stash drop # ── Option B : garder ta version, ignorer les changements distants ── # (uniquement si tu sais ce que tu fais) git pull origin main --strategy-option=ours

🔄 Cas 3 — Repartir proprement depuis la version du formateur

⚠ Destructif : Cette opération écrase toutes tes modifications locales sur les fichiers trackés. Tes .tfvars et fichiers ignorés par .gitignore sont préservés.
# Sauvegarder d'abord ton travail si besoin : cp tp-3tiers/terraform/main.tf ~/mon-main-tf.bak # Réinitialiser tous les fichiers trackés à la version distante : git fetch origin git reset --hard origin/main # Vérifier : git status # doit afficher "nothing to commit, working tree clean" ls tp-3tiers/ # nouveau TP visible

✅ Vérifier la mise à jour

💡 Bonne pratique : Avant chaque séance, lance git pull origin main depuis ~/3iac1-lab-starter. Si la commande affiche "Already up to date", tu es à jour. Si elle liste des fichiers, lis le message du commit (git log --oneline -1) pour savoir ce qui a changé.

💾 Persister les mises à jour dans l'OVA (pour les prochains démarrages ou duplications)

Un git pull ne modifie que le disque virtuel de la VM en cours d'exécution. Si tu éteins et relances la VM depuis l'OVA d'origine, ou si tu l'importes sur un autre PC, tu repars de la version initiale — sans les nouveaux TP. Pour conserver définitivement les mises à jour, tu as deux options selon ton hyperviseur.

Option 1 — Créer un snapshot VirtualBox (recommandé)

Un snapshot "fige" l'état complet de la VM à un instant T. Tu peux revenir à cet état à tout moment, ou t'en servir comme point de départ pour une nouvelle session.

Option 2 — Exporter une nouvelle OVA à partager

Si tu veux partager la VM mise à jour avec un autre étudiant ou l'importer sur un autre PC, exporte-la en OVA depuis VirtualBox.

Option 3 — Script de démarrage automatique (avancé)

Pour ne plus jamais avoir à penser à git pull, configure la VM pour le faire automatiquement à chaque connexion SSH ou ouverture de terminal.

⚠ Prérequis : La VM doit avoir accès à Internet au démarrage. Si le réseau n'est pas disponible (mode hors-ligne, VPN, proxy d'entreprise), le pull échoue silencieusement mais ne bloque pas la session.
