🔗 QCM — Terraform & Ansible en tandem

Utilisation conjointe des deux outils — Formation 3IAC1

📅 28 mai 2026 🎯 20 questions ⏱ ~30 min 📚 Niveau Bachelor 3
🟣 Terraform provisionne → generated.ini → 🟢 Ansible → configure output/

Q1
Quelle est la répartition des responsabilités entre Terraform et Ansible dans une chaîne IaC complète ?
✅ Bonne réponse : b)
La complémentarité est fondamentale : Terraform déclare et crée l'infrastructure (VMs, réseaux, stockage…) via des providers ; Ansible prend la main ensuite pour configurer ce qui vient d'être provisionné (paquets, fichiers de config, services…). Dans le projet : Terraform crée des fichiers locaux simulant des serveurs, Ansible les configure via des templates Jinja2.
Ce ne sont pas des outils interchangeables (c) : Terraform est déclaratif avec gestion d'état, Ansible est procédural/agentless. Chacun excelle dans son domaine.
Q2
Dans le projet, quel est l'ordre correct des étapes pour déployer l'environnement complet ?
✅ Bonne réponse : d)
L'ordre est impératif : 1) terraform init télécharge les providers ; 2) terraform apply crée les ressources et génère ansible/inventories/generated.ini ; 3) seulement alors, Ansible peut utiliser cet inventaire pour configurer les hôtes. Lancer Ansible avant Terraform (a) ferait échouer le playbook car l'inventaire n'existe pas encore.
Q3
Dans terraform/tp-final/main.tf, pourquoi la ressource local_file.ansible_inventory déclare-t-elle depends_on = [local_file.server_info] ?
✅ Bonne réponse : a)
depends_on force une dépendance d'ordre explicite. Ici, Terraform n'utilise pas les valeurs de server_info dans l'inventaire (pas de référence directe), donc il ne saurait pas seul dans quel ordre créer les deux ressources. depends_on garantit la cohérence fonctionnelle : les "serveurs" doivent exister avant que leur inventaire soit généré.
b) est faux : depends_on impose un ordre séquentiel, donc c'est l'opposé du parallélisme.
Q4
Dans terraform/tp-final/templates/inventory.tpl, Terraform génère le fichier generated.ini. Quel mécanisme Terraform est utilisé pour écrire le contenu de ce fichier ?
✅ Bonne réponse : c)
Dans tp-final/main.tf : resource "local_file" "ansible_inventory" { content = templatefile("${path.module}/templates/inventory.tpl", { servers = [...], environment = var.environment }) }. La fonction templatefile() rend le template inventory.tpl avec les variables Terraform (liste de serveurs, environnement), et la ressource local_file écrit le résultat sur le disque à l'emplacement attendu par Ansible.
Q5
La variable deploy_environment apparaît dans l'inventaire généré (generated.ini). D'où vient-elle et comment est-elle transmise à Ansible ?
✅ Bonne réponse : b)
C'est le cœur du passage de contexte entre les deux outils. Terraform possède var.environment = "development". Le template inventory.tpl inscrit deploy_environment=development sur chaque ligne d'hôte. Résultat dans generated.ini : 192.168.1.10 ansible_connection=local deploy_environment=development. Ansible lit cette valeur comme variable d'hôte, accessible dans les playbooks et templates via {{ deploy_environment }}.
Q6
Que se passe-t-il concrètement si on augmente var.instance_count de 2 à 4 dans Terraform et qu'on relance terraform apply, puis ansible-playbook ?
✅ Bonne réponse : d)
Grâce au méta-argument count et au state file, Terraform calcule le diff : 2 instances existent déjà (pas touchées), 2 nouvelles sont à créer. L'inventaire Ansible est régénéré avec 4 lignes. À la prochaine exécution d'Ansible, les 4 hôtes sont ciblés — les 2 anciens reçoivent un ok (idempotence), les 2 nouveaux reçoivent un changed. C'est la force de la chaîne automatisée.
Q7
Dans la chaîne du projet, quel est l'unique fichier produit par Terraform qui sert de "pont" vers Ansible ?
✅ Bonne réponse : c)
generated.ini est l'artefact clé du passage de relais. Terraform le génère via templatefile("inventory.tpl", ...) et le dépose exactement là où Ansible l'attend. Il contient les IPs, la connexion (ansible_connection=local) et les variables d'environnement. Sans ce fichier, Ansible n'a pas de cible : la commande ansible-playbook -i inventories/generated.ini échouerait.
terraform.tfstate (a) est interne à Terraform et ne doit jamais être lu directement par Ansible.
Q8
Pourquoi le fichier terraform.tfstate ne doit-il pas être commité dans Git, alors que .terraform.lock.hcl doit l'être ?
✅ Bonne réponse : a)
Le tfstate peut contenir des valeurs sensibles en clair (mots de passe de BDD, clés API…) même si elles sont déclarées sensitive = true dans les variables. Le commiter dans Git les exposerait dans l'historique. En équipe, le state est géré via un backend distant sécurisé (S3 + chiffrement, Terraform Cloud…). À l'inverse, .terraform.lock.hcl ne contient que des versions et hashes cryptographiques de providers : sans risque de sécurité, et utile pour garantir la reproductibilité des builds.
Q9
Quels sont les avantages de l'approche "inventaire dynamique généré par Terraform" par rapport à un inventaire Ansible statique écrit à la main ?
⚠️ Plusieurs réponses attendues
✅ Bonnes réponses : a) et c)
a) Vrai — Terraform connaît exactement les ressources qu'il a créées et leur IP réelle. Plus de risque de copier-coller une mauvaise IP dans un fichier INI.
c) Vrai — C'est la principale force de la chaîne : scalabilité automatique. Modifier instance_count et relancer suffit.
b) Faux — Ansible ne peut pas créer d'infrastructure. C'est le rôle exclusif de Terraform. Ansible configure ce qui existe.
d) Faux — ansible.cfg reste nécessaire pour configurer le comportement d'Ansible (chemin des rôles, host_key_checking…).
Q10
Dans le template inventory.tpl, les variables comme ${servers} utilisent la syntaxe HCL de Terraform, non la syntaxe Jinja2. Pourquoi est-ce important de ne pas les confondre ?
✅ Bonne réponse : d)
C'est une erreur classique en formation ! Les templates .tpl de Terraform utilisent ${variable} (HCL), rendus lors de terraform apply. Les templates .j2 d'Ansible utilisent {{ variable }} (Jinja2), rendus lors de l'exécution du playbook. Si on écrit {{ servers }} dans un template Terraform, la valeur ne sera jamais substituée par Terraform — le fichier généré contiendra le texte littéral {{ servers }}. Cette confusion est citée dans le fichier .ia/contexte-projet.md comme erreur fréquente à anticiper.
Q11
Dans deploy.yml, la tâche "Générer la configuration nginx" utilise le module template avec src: nginx.conf.j2. D'où vient la variable {{ deploy_environment }} utilisée dans ce template ?
✅ Bonne réponse : b)
C'est le passage de relais concret entre les deux outils. Dans generated.ini : 192.168.1.10 ansible_connection=local deploy_environment=development. Ansible lit cette variable d'hôte et la rend disponible dans tous les templates et tâches du playbook. Le filtre | default('development') dans nginx.conf.j2 sert de garde-fou si la variable était absente.
Q12
Pourquoi dit-on que Terraform est déclaratif et Ansible procédural ? Quelle conséquence pratique cela a-t-il ?
✅ Bonne réponse : c)
Terraform est déclaratif : on décrit "je veux 3 serveurs en production" et Terraform calcule lui-même quoi créer/modifier/détruire pour atteindre cet état (via le diff state). Ansible est plus procédural : on liste les tâches dans l'ordre — "crée ce dossier, puis copie ce fichier, puis lance ce service". L'idempotence d'Ansible compense partiellement cela, mais l'ordre des tâches reste important.
Q13
Dans le TP final, pourquoi crée-t-on d'abord les fichiers server-0.json, server-1.json via Terraform avant de lancer Ansible, plutôt que de laisser Ansible créer ces fichiers directement ?
✅ Bonne réponse : a)
La séparation des responsabilités est conceptuelle, pas seulement technique. Ces fichiers JSON représentent des métadonnées d'infrastructure (ce que serait une VM dans un vrai cloud). Terraform, outil de provisionning, est responsable de les créer. Ansible, outil de configuration, prend ensuite la main pour déployer l'application sur ces "serveurs". Respecter cette frontière rend la chaîne claire, maintenable et évolutive.
Q14
Que produit l'output Terraform server_ips dans tp-final/main.tf ? À quoi peut-il servir dans une vraie chaîne IaC ?
✅ Bonne réponse : d)
Les blocs output servent à deux choses : l'affichage lisible en fin de terraform apply, et la récupération programmatique via terraform output -json server_ips dans un script CI/CD. Dans une vraie pipeline (GitHub Actions, GitLab CI…), on pourrait récupérer les IPs avec cette commande et les passer dynamiquement à Ansible, évitant même l'étape de génération d'inventaire fichier.
Q15
Quels fichiers du projet doivent être ajoutés au .gitignore ? Lesquels doivent être commités ?
⚠️ Sélectionnez les fichiers qui doivent être commités dans Git
✅ Bonnes réponses : b) et d)
b) Commiter ✅ — .terraform.lock.hcl : versionnage des providers, sans donnée sensible.
d) Commiter ✅ — Les playbooks, templates, variables et rôles sont du code source IaC — ils doivent être versionnés.

Q16
Dans une pipeline CI/CD (ex. GitHub Actions), dans quel ordre typique enchaîne-t-on les étapes Terraform et Ansible ?
✅ Bonne réponse : c)
L'ordre est logique et impératif : on ne peut pas configurer une infrastructure qui n'existe pas encore. En CI/CD : 1) terraform init (télécharge les providers) ; 2) terraform plan (revue humaine ou automatique) ; 3) terraform apply -auto-approve (provisionne et génère l'inventaire) ; 4) ansible-playbook -i generated.ini deploy.yml (configure). On peut aussi ajouter des étapes de lint (terraform validate, ansible-lint) avant les apply.
Q17
L'IaC (Infrastructure as Code) implique que toute la configuration est décrite dans des fichiers versionnés. Quels bénéfices concrets cela apporte-t-il par rapport à une configuration manuelle via une interface graphique (ClickOps) ? (plusieurs réponses possibles)
⚠️ Plusieurs réponses attendues
✅ Bonnes réponses : a), c) et d)
a) Vrai — C'est l'avantage fondamental : mêmes fichiers → même infra, partout. Fini le "ça marche chez moi".
c) Vrai — Chaque git commit est une trace auditée : qui a augmenté instance_count, quand, avec quel message.
d) Vrai — Les fichiers peuvent être exécutés automatiquement dans une pipeline sans cliquer dans une console cloud.
b) Faux — L'IaC ne garantit pas l'absence de panne. Elle facilite la récupération (on peut relancer depuis les fichiers), mais des bugs peuvent exister dans le code lui-même.
Q18
Dans le projet, la variable var.environment de Terraform et la variable app_environment du rôle Ansible ont des noms différents. Comment s'assure-t-on qu'elles désignent bien le même environnement de déploiement ?
✅ Bonne réponse : d)
La chaîne de transmission est : var.environment (Terraform) → template inventory.tpl → deploy_environment=development dans generated.ini → variable d'hôte Ansible → {{ deploy_environment }} dans deploy.yml → peut être passée au rôle via ses variables. Il faut donc être vigilant sur cette chaîne de nommage lors du développement.
Q19
Si on veut tester uniquement la partie Ansible (sans relancer Terraform), quelle condition préalable est nécessaire ?
✅ Bonne réponse : b)
Ansible a besoin d'un inventaire pour fonctionner. Si generated.ini existe déjà (Terraform a déjà été appliqué), on peut relancer Ansible directement avec -i inventories/generated.ini. Alternativement, le projet fournit hosts.ini (inventaire statique avec localhost) pour les TP indépendants de Terraform. terraform plan (c) ne génère aucun fichier : il affiche seulement ce qui serait fait.
Q20
En conditions réelles (cloud AWS, Azure…), quelles affirmations sur la chaîne Terraform + Ansible sont vraies ?
⚠️ Plusieurs réponses attendues
✅ Bonnes réponses : a), c) et d)
a) Vrai — En cloud réel, Terraform crée des aws_instance avec de vraies IPs, et les écrit dans l'inventaire via un template similaire à celui du TP final.
c) Vrai — En production, Ansible se connecte en SSH aux VMs distantes. ansible_connection=local est spécifique aux TP sans accès cloud de ce projet.
d) Vrai — Indispensable en équipe : backend S3 + DynamoDB pour le lock (AWS), Azure Blob + table de lock, ou Terraform Cloud.
b) Faux — Bien qu'Ansible ait des modules cloud, c'est une mauvaise pratique : Terraform est bien supérieur pour gérer le cycle de vie des ressources cloud (state, diff, destroy). La séparation des rôles reste la meilleure approche.
