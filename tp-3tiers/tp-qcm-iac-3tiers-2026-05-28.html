ÉTAPE 1
Ansible
Installer Docker sur l'OVA via un playbook Ansible
Prérequis indispensable avant toute utilisation du provider Terraform Docker
Contexte : L'OVA est une Ubuntu 22.04 fraîche. Avant que Terraform puisse provisionner des conteneurs Docker, il faut que Docker soit installé et opérationnel. Ansible se charge de cette étape de bootstrap. Trois paquets sont nécessaires : docker.io (le daemon), docker-compose-plugin et python3-docker (requis par le provider Terraform kreuzwerker/docker).
🎯 Objectif
Docker installé, service démarré, utilisateur courant dans le groupe docker (pour éviter le sudo permanent).
▶ TESTEZ SUR VOTRE OVA — après avoir appliqué votre choix :
cd tp-3tiers/ansible
ansible-playbook -i inventories/hosts.ini playbooks/01-install-docker.yml
docker --version          # doit afficher Docker 24+
docker run --rm hello-world   # doit réussir sans sudo

✅ Bonne réponse : C
C est correct — Installe les 3 paquets nécessaires en une seule tâche apt (efficace, idempotent), démarre et active Docker au boot (enabled: yes), puis ajoute l'utilisateur au groupe docker avec append: yes pour ne pas écraser ses groupes existants. python3-docker est indispensable : c'est le SDK Python qu'utilise le provider Terraform kreuzwerker/docker pour piloter Docker via l'API.
A — Manque become: yes sur les tâches apt et service. Sans élévation de privilèges, la tâche échoue avec Permission denied. Oubli classique.
B — pip install docker installe uniquement le SDK Python, pas le daemon Docker. Le service docker n'existerait pas et la tâche service échouerait.
D — L'ordre est inversé : on tente de démarrer un service qui n'est pas encore installé. Ansible retournera Could not find the requested service.
ÉTAPE 2
Terraform
Définir les 3 réseaux Docker avec la bonne segmentation de sécurité
dmz_net · app_net · db_net — isolation et règles d'accès
Contexte : La sécurité réseau est la première ligne de défense. L'architecture impose trois zones : dmz_net (nginx accessible de l'hôte), app_net (nginx ↔ Flask, invisible de l'extérieur), db_net (Flask ↔ PostgreSQL ↔ Redis, complètement isolé — aucun accès Internet possible). Le paramètre internal = true de Docker interdit tout trafic sortant du réseau.
🎯 Objectif
Trois réseaux créés. La base de données ne doit jamais être joignable depuis l'extérieur de Docker, même en cas d'erreur de configuration d'un conteneur.
▶ TESTEZ SUR VOTRE OVA :
cd tp-3tiers/terraform && terraform init && terraform apply
docker network ls                        # doit lister dmz_net, app_net, db_net
docker network inspect db_net | grep Internal   # doit afficher "Internal": true

Quel bloc Terraform définit correctement les 3 réseaux avec la segmentation de sécurité requise ?

A 3 réseaux distincts — db_net isolé avec internal = true PROD-READY 
resource "docker_network" "dmz_net" {
  name = "dmz_net"
}

resource "docker_network" "app_net" {
  name = "app_net"
}

resource "docker_network" "db_net" {
  name     = "db_net"
  internal = true  # aucun accès Internet — réseau fermé
}
B 3 réseaux sans isolation du réseau base de données FAILLE SÉCU 
resource "docker_network" "dmz_net" {
  name = "dmz_net"
}
resource "docker_network" "app_net" {
  name = "app_net"
}
resource "docker_network" "db_net" {
  name = "db_net"
  # internal manquant — DB accessible depuis Internet
}
C Réseau unique pour tous les services PAS DE SEGMENTATION

  name = "main_net"
  # tous les conteneurs sur le même réseau
  # nginx peut atteindre postgres directement
}
D dmz_net et db_net tous deux en internal ARCHITECTURE BRISÉE 
resource "docker_network" "dmz_net" {
  name     = "dmz_net"
  internal = true  # ← erreur : nginx ne recevra plus rien
}
resource "docker_network" "app_net" {
  name = "app_net"
}
resource "docker_network" "db_net" {
  name     = "db_net"
  internal = true
}
✅ Bonne réponse : A
A est correct — Seul db_net est déclaré internal = true. Cela signifie que Docker refuse toute route sortante depuis ce réseau. Un conteneur PostgreSQL compromis ne pourrait pas initier de connexion vers Internet pour exfiltrer des données. dmz_net et app_net restent routables (nécessaire pour puller des images, ou pour que l'app contacte une API externe).
B — Sans internal = true sur db_net, la base de données pourrait théoriquement initier des connexions sortantes. En cas de compromission via SQL injection, l'attaquant peut exfiltrer via outbound.
C — Zéro segmentation. Nginx pourrait contacter Postgres directement, un bug dans nginx exposerait la DB. Inacceptable en production.
D — internal = true sur dmz_net coupe nginx de l'hôte : les requêtes HTTP de l'utilisateur n'arriveraient jamais. L'application est inaccessible.
ÉTAPE 3
Terraform
Déclarer le conteneur PostgreSQL — sécurité et persistance
Réseau isolé · aucun port exposé · volume persistant · restart policy
Contexte : PostgreSQL est le service le plus sensible de l'architecture. Trois règles de sécurité s'appliquent : (1) il doit être uniquement sur db_net, (2) aucun port ne doit être exposé sur l'hôte (le port 5432 ne doit pas apparaître dans docker ps), (3) les données doivent survivre à un redémarrage via un volume nommé.
🎯 Objectif
docker ps ne montre pas de port publié pour postgres. docker volume ls montre pg_data. docker inspect postgres | grep Networks ne montre que db_net.
▶ TESTEZ SUR VOTRE OVA :
terraform apply
docker ps --format "table {{.Names}}\t{{.Ports}}"
# postgres ne doit pas avoir de port listé (colonne PORTS vide)
docker exec -it flask_app python -c \
  "import psycopg2; psycopg2.connect(host='postgres',dbname='app',user='app',password='...')"
# doit réussir (app sur db_net peut joindre postgres)

Quel bloc Terraform définit le conteneur PostgreSQL de façon correcte et sécurisée ?

A PostgreSQL avec port 5432 mappé sur l'hôte FAILLE SÉCU 
resource "docker_container" "postgres" {
  name  = "postgres"

  env = [

    "POSTGRES_USER=${var.db_user}",
    "POSTGRES_PASSWORD=${var.db_password}",
  ]

  volumes {
    volume_name    = docker_volume.pg_data.name
    container_path = "/var/lib/postgresql/data"
  }
}
B PostgreSQL sur app_net — mauvaise zone réseau MAUVAISE ZONE

  name  = "postgres"
  image = "postgres:15-alpine"

  networks_advanced { name = docker_network.app_net.name }

  env = [
    "POSTGRES_DB=${var.db_name}",
    "POSTGRES_USER=${var.db_user}",
    "POSTGRES_PASSWORD=${var.db_password}",
  ]

  volumes {
    volume_name    = docker_volume.pg_data.name
    container_path = "/var/lib/postgresql/data"
  }
}
C PostgreSQL sans volume persistant PERTE DE DONNÉES 
resource "docker_container" "postgres" {
  name  = "postgres"
  image = "postgres:15-alpine"

  networks_advanced { name = docker_network.db_net.name }

  env = [
    "POSTGRES_DB=${var.db_name}",
    "POSTGRES_USER=${var.db_user}",
    "POSTGRES_PASSWORD=${var.db_password}",
  ]
  # volumes {} absent → toutes les données perdues au restart
}
D PostgreSQL — db_net, sans port, volume + restart policy PROD-READY 
resource "docker_container" "postgres" {
  name    = "postgres"
  image   = "postgres:15-alpine"
  restart = "unless-stopped"  # redémarre si crash

  networks_advanced { name = docker_network.db_net.name }
  # aucun bloc ports{} → 5432 jamais exposé sur l'hôte

  env = [
    "POSTGRES_DB=${var.db_name}",
    "POSTGRES_USER=${var.db_user}",
    "POSTGRES_PASSWORD=${var.db_password}",
  ]

  volumes {
    volume_name    = docker_volume.pg_data.name
    container_path = "/var/lib/postgresql/data"
  }
}
✅ Bonne réponse : D
D est correct — Trois règles respectées : (1) uniquement sur db_net (isolé) ; (2) absence de bloc ports {} → le port 5432 ne sera jamais accessible depuis l'hôte ou l'extérieur ; (3) volume nommé pg_data monté sur /var/lib/postgresql/data → les données survivent aux redémarrages et aux terraform apply. Le restart = "unless-stopped" garantit la haute disponibilité après un crash.
A — external = 5432 expose le port sur toutes les interfaces de l'hôte. N'importe quelle machine sur le réseau local peut alors se connecter à PostgreSQL avec les bons credentials. Catastrophique en production.
B — Sur app_net, nginx (également sur app_net) pourrait joindre PostgreSQL directement, contournant la couche applicative. La segmentation en 3 zones perd tout son sens.
C — Sans volume, les données PostgreSQL sont stockées dans la couche writable du conteneur. Un terraform apply (qui recrée le conteneur) ou un crash Docker efface toutes les données. Inadmissible en production.
ÉTAPE 4
Ansible + Vault
Configurer nginx comme reverse proxy sécurisé + gérer les secrets avec Vault
Headers sécurité · rate limiting · proxy_pass · chiffrement des secrets
Contexte : Nginx est le seul point d'entrée public (le "reverse proxy" / "point d'entrée DMZ"). Sa configuration doit : (1) proxy_pass vers le nom du conteneur Flask (pas localhost — Docker résout les noms de conteneurs sur le réseau app_net) ; (2) masquer la version serveur (server_tokens off) ; (3) ajouter les headers de sécurité HTTP ; (4) limiter le débit (limit_req). Les mots de passe DB/Redis doivent être chiffrés via ansible-vault encrypt_string — jamais en clair dans Git.
🎯 Objectif
curl -I http://localhost ne révèle pas la version nginx. Les headers X-Frame-Options, X-Content-Type-Options sont présents. Depuis tp-3tiers/ansible/ : ansible-vault view group_vars/all.yml montre les secrets chiffrés (!vault).
▶ TESTEZ SUR VOTRE OVA :
cd tp-3tiers/ansible
ansible-playbook -i inventories/hosts.ini playbooks/04-configure.yml --ask-vault-pass
curl -I http://localhost          # vérifier les headers
curl -s http://localhost/         # doit retourner la réponse Flask
# Test rate limiting (doit bloquer après 10 req/s) :
for i in $(seq 1 15); do curl -s -o /dev/null -w "%{http_code}\n" http://localhost; done

Quelle combinaison nginx.conf.j2 + gestion des secrets est correcte pour une configuration production ?

A proxy_pass vers localhost + secrets en clair dans vars 2 ERREURS 
# nginx.conf.j2
server {
    listen 80;
    location / {
        proxy_pass http://localhost:5000;  # ← faux en Docker
        proxy_set_header Host $host;
    }
}

# group_vars/all.yml
db_password: "monMotDePasse123"   # ← en clair dans Git !
B proxy_pass container name · headers sécu · rate limiting · Vault PROD-READY 
# nginx.conf.j2
limit_req_zone $binary_remote_addr zone=app:10m rate=10r/s;

server {
    listen        80;
    server_tokens off;   # masque la version nginx

    add_header X-Frame-Options       "SAMEORIGIN";
    add_header X-Content-Type-Options "nosniff";
    add_header X-XSS-Protection       "1; mode=block";
    add_header Referrer-Policy        "strict-origin";

    location / {
        limit_req        zone=app burst=20 nodelay;
        proxy_pass       http://flask_app:5000;  # nom conteneur Docker
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_hide_header X-Powered-By;
    }
}

# group_vars/all.yml — secrets chiffrés avec ansible-vault
# ansible-vault encrypt_string 'monMotDePasse123' --name 'db_password'
db_password: !vault |
  $ANSIBLE_VAULT;1.1;AES256
  61383937623466323538316666346339...
C proxy_pass correct mais server_tokens on, sans headers ni vault CONFIG PARTIELLE 
# nginx.conf.j2
server {
    listen        80;
    server_tokens on;  # ← expose "nginx/1.25.3" dans les headers

    location / {
        proxy_pass       http://flask_app:5000;
        proxy_set_header Host $host;
        # aucun header de sécurité
    }
}

# group_vars/all.yml
db_password: "{{ lookup('env','DB_PASSWORD') }}"
# dépend d'une variable shell non contrôlée
D proxy_pass pointant directement vers PostgreSQL LOGIQUE BRISÉE 
# nginx.conf.j2
server {
    listen        80;
    server_tokens off;

    location / {
        proxy_pass http://postgres:5432;
        # nginx fait du HTTP, postgres attend du SQL binaire
        # nginx et postgres ne sont pas sur le même réseau
        proxy_set_header Host $host;
    }
}
✅ Bonne réponse : B
B est correct — Cinq points critiques réunis : (1) proxy_pass http://flask_app:5000 utilise le nom du conteneur Docker comme hostname — c'est ainsi que fonctionne la résolution DNS interne Docker (via le réseau app_net partagé par nginx et flask_app) ; (2) server_tokens off empêche un attaquant de cibler une CVE spécifique à la version nginx ; (3) les 4 headers de sécurité HTTP bloquent le clickjacking, le MIME sniffing et les XSS ; (4) limit_req protège contre le brute-force et le DDoS applicatif ; (5) !vault garantit que les secrets ne transitent jamais en clair dans Git.
A — proxy_pass http://localhost:5000 : dans Docker, chaque conteneur a son propre localhost. nginx essaierait de joindre son propre port 5000, qui n'existe pas. Erreur 502 garantie.
C — server_tokens on expose la version nginx exacte dans chaque réponse HTTP. Un attaquant peut cibler directement les CVE connues de cette version. lookup('env',...) dépend d'une variable shell qui peut ne pas être définie en CI/CD.
D — Nginx et postgres ne partagent aucun réseau commun (nginx est sur dmz_net+app_net, postgres sur db_net). De plus, nginx parle HTTP, postgres attend le protocole wire de PostgreSQL — incompatible.
ÉTAPE 5
Terratest
Valider l'infrastructure avec Terratest (Go)
Test d'intégration IaC · vérifier les réseaux Docker · tester l'endpoint HTTP
Contexte : Terratest est le framework de test Go de référence pour valider l'IaC. Il exécute un terraform apply, vérifie l'état réel de l'infrastructure, puis fait un terraform destroy automatique. Ici, le test doit : (1) vérifier que le réseau db_net est bien marqué Internal: true via l'API Docker ; (2) vérifier que l'endpoint HTTP nginx répond 200 OK ; (3) nettoyer après lui avec defer terraform.Destroy().
🎯 Objectif
go test -v -timeout 10m ./test/ passe sans erreur. Le test garantit que la segmentation réseau et le reverse proxy fonctionnent à chaque modification de l'IaC.
▶ TESTEZ SUR VOTRE OVA :
cd tp-3tiers/test/
go mod init 3iac1-test && go mod tidy
# (installe gruntwork-io/terratest et docker/docker)
go test -v -timeout 10m -run TestInfrastructure3Tiers .

func TestInfrastructure3Tiers(t *testing.T) {
    opts := &terraform.Options{
        TerraformDir: "../terraform",
    }

    // Cleanup automatique, même en cas d'échec
    defer terraform.Destroy(t, opts)

    terraform.InitAndApply(t, opts)

    // ── Test 1 : db_net doit être interne (isolé)
    cli, _ := client.NewClientWithOpts(client.FromEnv)
    net, _ := cli.NetworkInspect(
        context.Background(), "db_net",
        types.NetworkInspectOptions{},
    )
    assert.True(t, net.Internal,
        "db_net doit être internal=true")

    // ── Test 2 : nginx doit répondre 200
    http_helper.HttpGetWithRetry(
        t,
        "http://localhost",
        nil,
        200,
        "OK",
        5,
        10*time.Second,
    )
}
D Test avec sleep fixe au lieu de retry + pas de vérification réseau FRAGILE 
func TestInfrastructure3Tiers(t *testing.T) {
    opts := &terraform.Options{
        TerraformDir: "../terraform",
    }
    defer terraform.Destroy(t, opts)
    terraform.InitAndApply(t, opts)

    time.Sleep(30 * time.Second)  // ← fragile : dépend de la machine

    resp, err := http.Get("http://localhost")
    require.NoError(t, err)
    assert.Equal(t, 200, resp.StatusCode)
    // pas de test sur internal=true pour db_net
}
✅ Bonne réponse : C
C est correct — Quatre bonnes pratiques Terratest réunies : (1) defer terraform.Destroy() placé immédiatement après la déclaration des options garantit le cleanup même si le test panique ; (2) InitAndApply regroupe init + apply en une seule call ; (3) l'inspection Docker vérifie que db_net.Internal == true — c'est un test de sécurité infrastructure, pas juste un test fonctionnel ; (4) HttpGetWithRetry retente N fois avec un délai, robuste aux temps de démarrage variables des conteneurs.
A — Sans defer terraform.Destroy(), si le test échoue, l'infrastructure reste en place. Dans une pipeline CI/CD, cela consomme des ressources indéfiniment et pollue les runs suivants.
B — terraform.Destroy() avant Apply échoue car il n'y a rien à détruire. Attendre un StatusCode 500 comme succès de test est une erreur de logique : on teste que l'app plante, pas qu'elle fonctionne.
D — time.Sleep(30s) est une anti-pattern Terratest : trop court sur une machine lente, trop long sur une machine rapide. HttpGetWithRetry avec timeout est toujours préférable. L'absence de test sur internal=true laisse passer une régression de sécurité silencieusement.
