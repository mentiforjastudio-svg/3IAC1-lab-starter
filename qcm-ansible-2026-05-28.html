Q1
Quelle est la principale caractéristique architecturale d'Ansible qui le distingue d'outils comme Chef ou Puppet ?
✅ Bonne réponse : c)
L'architecture agentless est la marque de fabrique d'Ansible. Contrairement à Chef ou Puppet qui nécessitent un agent en permanence sur les machines gérées, Ansible n'a besoin que d'une connexion SSH (ou ansible_connection=local pour les TP du projet). Cela simplifie la mise en place et la maintenance.
b) décrit le modèle agent-based de Chef/Puppet, l'opposé d'Ansible.
Q2
Quel est le rôle du fichier ansible.cfg dans un projet Ansible ?
✅ Bonne réponse : d)
ansible.cfg est le fichier de configuration globale. Dans le projet, il définit : inventory = ./inventories/hosts.ini, roles_path = ./roles, host_key_checking = False et stdout_callback = yaml. Il évite de répéter ces options à chaque ligne de commande.
Les hôtes sont dans l'inventaire hosts.ini (a), les tâches dans les playbooks (b), et les secrets dans Ansible Vault (c).
Q3
Dans l'inventaire du projet, les hôtes sont déclarés avec ansible_connection=local. Qu'est-ce que cela implique ?
✅ Bonne réponse : a)
ansible_connection=local indique à Ansible de ne pas utiliser SSH et d'exécuter les tâches directement sur la machine qui lance la commande. C'est le mode utilisé dans tous les TP du projet (contrainte : pas d'accès à un vrai cloud ni à des VMs distantes). Voir hosts.ini : localhost ansible_connection=local.
Q4
Qu'est-ce qu'un playbook Ansible ?
✅ Bonne réponse : b)
Un playbook est un fichier YAML structuré en plays. Chaque play cible un groupe d'hôtes (hosts: webservers) et contient une liste de tâches (tasks:). On peut avoir plusieurs plays dans un même playbook. Le projet contient 4 playbooks : setup-system.yml, generate-config.yml, use-role.yml, deploy.yml.
Q5
Que signifie le principe d'idempotence dans le contexte d'Ansible ?
✅ Bonne réponse : c)
L'idempotence signifie qu'une opération appliquée N fois donne le même résultat qu'appliquée une seule fois. Dans setup-system.yml, si les dossiers existent déjà, Ansible ne les recrée pas — il signale ok au lieu de changed. Le module file avec state: directory est idempotent par nature. La tâche copy avec force: no illustre aussi ce principe.
Q6
Quel module Ansible est utilisé pour créer des répertoires et gérer leurs permissions ?
✅ Bonne réponse : d)
Le module file gère la création, la suppression et les permissions des fichiers et répertoires. Avec state: directory il crée un dossier, avec state: absent il le supprime. Dans setup-system.yml : file: path: "{{ config_dir }}" state: directory mode: '0755'. C'est l'un des modules les plus utilisés du projet.
copy copie un contenu statique dans un fichier, template rend un template Jinja2, command exécute une commande shell sans idempotence garantie.
Q7
Dans un template Jinja2 utilisé par Ansible, quelle syntaxe permet d'afficher la valeur de la variable app_name ?
✅ Bonne réponse : a)
Jinja2 utilise {{ variable }} pour l'interpolation de valeurs. On le voit partout dans les templates du projet : "name": "{{ app_name | default('MyApp') }}" dans app-config.json.j2, ou server_name {{ inventory_hostname }}; dans nginx.conf.j2. Attention : c'est différent de la syntaxe HCL de Terraform qui utilise aussi ${variable}.
Q8
Quelles affirmations sur les handlers Ansible sont vraies ?
⚠️ Plusieurs réponses attendues
✅ Bonnes réponses : b) et d)
b) Vrai — Les handlers sont collectés tout au long du play et exécutés une seule fois, en fin de play. Si 3 tâches notifient le même handler, il ne tourne qu'une seule fois.
d) Vrai — Si aucune tâche ne déclenche de changement (changed), le handler n'est pas exécuté. Dans le rôle app-config, le handler "Recharger configuration" n'est appelé que si le template app.conf.j2 a réellement changé.
a) Faux — Ils s'exécutent en fin de play, pas immédiatement.
c) Faux — Les handlers complètent les tâches ; ils ne les remplacent pas.
Q9
Que fait le module debug dans un playbook Ansible ?
✅ Bonne réponse : c)
debug est un module de traçabilité qui affiche du texte (msg:) ou la valeur d'une variable (var:) dans la sortie d'Ansible. Il est très utilisé pour vérifier l'état des variables entre les tâches. Dans deploy.yml : debug: msg: "Serveur : {{ inventory_hostname }} | Environnement : {{ deploy_environment }}". Il ne modifie rien sur l'hôte.
Q10
Quelle directive YAML dans un playbook permet d'élever les privilèges (équivalent de sudo) ?
✅ Bonne réponse : d)
become: yes (ou become: true) demande à Ansible d'élever les privilèges via sudo (par défaut). On peut le définir au niveau du play ou d'une tâche individuelle. Dans le projet, tous les playbooks utilisent become: no car les TP sont exécutés en local sans besoin de root. sudo: yes (a) est l'ancienne syntaxe, dépréciée.
Q11
Dans setup-system.yml, une tâche utilise register: created_files. À quoi sert le mot-clé register ?
✅ Bonne réponse : a)
register capture la sortie complète d'une tâche (code retour, stdout, stderr, liste de fichiers…) dans une variable. Dans setup-system.yml, register: created_files stocke le résultat du module find, puis la tâche suivante itère dessus avec loop: "{{ created_files.files }}". C'est le mécanisme central pour chaîner des tâches qui dépendent du résultat des précédentes.
Q12
Quelle est la différence entre les modules copy et template ?
✅ Bonne réponse : c)
Dans setup-system.yml, copy: content: "APP_NAME={{ app_name }}\n..." écrit un contenu statique (l'interpolation se fait dans le playbook YAML lui-même, pas dans un fichier). Le module template lit un fichier .j2 depuis le contrôleur, le rend avec Jinja2 (boucles, conditions, filtres…) puis l'envoie sur l'hôte. Voir deploy.yml qui utilise template: src: nginx.conf.j2.
Q13
Dans un rôle Ansible, quel est le rôle du dossier defaults/ (ex. : roles/app-config/defaults/main.yml) ?
✅ Bonne réponse : b)
defaults/main.yml contient les valeurs par défaut des variables du rôle. C'est la priorité la plus basse dans la hiérarchie des variables Ansible : n'importe quelle variable déclarée dans le playbook appelant, dans l'inventaire ou dans vars/ prend le dessus. Dans app-config/defaults/main.yml : app_port: 8080, app_environment: "development"…, tous surchargeables depuis use-role.yml.
Les dépendances de rôles (d) sont dans meta/main.yml, comme on le voit dans roles/app-config/meta/main.yml avec dependencies: [].
Q14
Quelles affirmations sur les rôles Ansible sont vraies ?
⚠️ Plusieurs réponses attendues
✅ Bonnes réponses : a) et c)
a) Vrai — Un rôle regroupe dans une arborescence standardisée : tasks/, handlers/, templates/, defaults/, meta/… C'est le mécanisme de réutilisabilité principal d'Ansible.
c) Vrai — Dans use-role.yml : roles: - role: app-config vars: .... Le playbook reste nécessaire pour cibler les hôtes et passer les variables.
b) Faux — Le playbook reste indispensable : c'est lui qui définit hosts: et appelle le rôle.
d) Faux — Les rôles peuvent (et doivent) avoir des handlers. Le rôle app-config en a un : "Recharger configuration".
Q15
Que fait le filtre Jinja2 | default('valeur') dans un template Ansible comme {{ app_name | default('MyApp') }} ?
✅ Bonne réponse : d)
Le filtre | default('valeur') est un garde-fou : si la variable n'est pas définie, Jinja2 retourne la valeur de repli au lieu de lever une erreur undefined. C'est très utilisé dans app-config.json.j2 : {{ app_name | default('MyApp') }}, {{ server_port | default(8080) }}. Si la variable est définie, sa valeur réelle est utilisée normalement.
Q16
Dans le template nginx.conf.j2, le bloc {% if deploy_environment == 'production' %} ... {% endif %} sert à :
✅ Bonne réponse : b)
Dans Jinja2, {% if condition %} ... {% endif %} est une structure conditionnelle : le bloc de texte entre les balises n'est rendu dans le fichier final que si la condition est vraie. Dans nginx.conf.j2, les directives access_log et error_log n'apparaissent que si deploy_environment == 'production'. Cela permet un seul template pour plusieurs environnements.
Pour boucler (c), Jinja2 utilise {% for item in liste %} ... {% endfor %}, comme dans app-config.json.j2 pour la liste des features.
Q17
Quelle commande permet de lancer le playbook deploy.yml avec l'inventaire généré par Terraform ?
✅ Bonne réponse : c)
La commande correcte est ansible-playbook (avec tiret, pas d'espace). Le flag -i (ou --inventory) spécifie l'inventaire à utiliser. Cette commande est documentée en commentaire en tête de deploy.yml : # Lancement : ansible-playbook -i inventories/generated.ini playbooks/deploy.yml. Sans -i, Ansible utilise l'inventaire par défaut défini dans ansible.cfg.
Q18
Dans app-config.json.j2, la boucle {% for feature in features %} ... {% endfor %} produit :
✅ Bonne réponse : a)
La boucle Jinja2 {% for feature in features %} itère sur chaque élément de la liste. Dans le template, elle génère une ligne JSON "feature" par élément, avec {{ "," if not loop.last else "" }} pour gérer la virgule de séparation JSON (sauf sur le dernier élément). Pour features: ["user_auth", "api_v2", "caching"], elle produit 3 lignes dans le tableau JSON.
Q19
Quelle variable Ansible magique contient le nom de l'hôte tel que défini dans l'inventaire ?
✅ Bonne réponse : d)
inventory_hostname est une variable magique Ansible qui contient exactement le nom de l'hôte tel qu'écrit dans l'inventaire. On la voit dans deploy.yml : "Serveur : {{ inventory_hostname }}" et dans nginx.conf.j2 : server_name {{ inventory_hostname }}. Elle vaut 192.168.1.10 si c'est ce qui est écrit dans generated.ini.
ansible_host (a) est l'IP de connexion réelle (peut différer si on utilise un alias). ansible_nodename (c) est le hostname système de la machine cible.
Q20
Dans la chaîne Terraform → Ansible, quels sont les avantages de générer generated.ini depuis Terraform et de l'utiliser comme inventaire pour Ansible ?
⚠️ Plusieurs réponses attendues
✅ Bonnes réponses : a), b) et c)
a) Vrai — Terraform écrit directement les IPs qu'il a attribuées ; aucune saisie manuelle ne peut se tromper.
b) Vrai — Dans generated.ini.example : 192.168.1.10 ansible_connection=local deploy_environment=development. La variable deploy_environment vient de Terraform et est disponible dans Ansible via {{ deploy_environment }}.
c) Vrai — C'est la force du fil rouge pédagogique du projet : une seule source de vérité, une chaîne automatisée de bout en bout.
d) Faux — Ansible ne modifie jamais le tfstate. La communication entre les deux outils est unidirectionnelle dans ce projet : Terraform → inventaire → Ansible.
