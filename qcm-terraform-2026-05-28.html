🟣 QCM Terraform

Révisions pour l'examen — Formation 3IAC1

📅 28 mai 2026 🎯 20 questions ⏱ ~25 min 📚 Niveau Bachelor 3

Q1
Que fait la commande terraform init ?
✅ Bonne réponse : d)
terraform init initialise le répertoire courant : il lit le bloc required_providers, télécharge les plugins (providers) depuis le registry et installe les modules référencés. C'est toujours la première commande à exécuter dans un nouveau projet ou après modification des dépendances.
Les autres options décrivent terraform plan (a), terraform apply (b) et terraform validate (c).
Q2
Dans le bloc suivant, que signifie ~> 2.0 comme contrainte de version ?
Code : version = "~> 2.0"
✅ Bonne réponse : a)
L'opérateur ~> est dit "pessimistic constraint operator". ~> 2.0 autorise 2.0, 2.1, 2.9… mais bloque 3.0. C'est la forme recommandée pour éviter les breaking changes tout en bénéficiant des correctifs mineurs.
Attention : ~> 2.0 et ~> 2.0.0 ne sont pas identiques. Le second n'autoriserait que les patches (2.0.x).
Q3
Quel fichier Terraform stocke l'état courant de l'infrastructure gérée ?
✅ Bonne réponse : c)
terraform.tfstate est le fichier d'état (state file). Il contient la représentation JSON de toutes les ressources gérées par Terraform : leurs attributs, leurs dépendances, leur ID réel chez le provider. Terraform s'en sert pour calculer le diff lors d'un plan.
.terraform.lock.hcl (b) verrouille les versions des providers, pas l'état de l'infra. Il doit être commité dans Git, contrairement au tfstate qui contient souvent des secrets.
Q4
Une variable est déclarée avec sensitive = true. Quelles affirmations sont vraies ?
⚠️ Plusieurs réponses attendues
✅ Bonnes réponses : b) et d)
b) Vrai — Terraform masque les valeurs sensibles dans les sorties console avec (sensitive value).
d) Vrai — Le mécanisme TF_VAR_nom est la méthode recommandée pour injecter des secrets sans les écrire dans un fichier.
a) Faux — On peut utiliser une variable sensible dans un output, mais l'output doit lui aussi être déclaré sensitive = true.
c) Faux — La valeur est tout de même stockée dans le tfstate, en clair. C'est pourquoi le state file doit être sécurisé (chiffrement, backend distant).
Q5
Quelle est la différence entre terraform plan et terraform apply ?
✅ Bonne réponse : a)
terraform plan calcule et affiche le diff entre l'état courant (tfstate) et la configuration désirée, sans modifier quoi que ce soit. C'est une étape de revue indispensable. terraform apply exécute réellement les créations/modifications/destructions et met à jour le tfstate.
b) est un piège classique : apply ne fait pas exactement la même chose que plan ; il recalcule le plan ET l'exécute.
Q6
Dans un module, quelle expression retourne le chemin absolu du répertoire contenant le fichier .tf courant ?
✅ Bonne réponse : d)
path.module retourne le chemin du répertoire où se trouve le module en cours d'évaluation. On s'en sert pour construire des chemins relatifs vers des templates : templatefile("${path.module}/templates/config.tpl", ...). C'est ce qu'on voit dans les modules du projet.
path.root pointe vers le module racine, et path.cwd vers le répertoire de travail courant — deux notions différentes dans les modules imbriqués.
Q7
Que produit l'expression suivante dans Terraform ?
[for i in range(3) : "server-${i}"]
✅ Bonne réponse : c)
La for expression avec crochets [...] produit une liste. range(3) retourne [0, 1, 2]. L'interpolation donne ["server-0", "server-1", "server-2"]. Ce pattern est utilisé dans le tp-final : [for i in range(var.instance_count) : "192.168.1.${10 + i}"].
range commence à 0, donc d) est incorrect. Les accolades {...} produiraient une map, pas les crochets.
Q8
Quel est le rôle du méta-argument count dans une ressource Terraform ?
✅ Bonne réponse : a)
count = N duplique la ressource N fois. Chaque instance est accessible via count.index (0 à N-1). Dans le tp-final : count = var.instance_count et filename = "server-${count.index}.json" permettent de créer N fichiers en une seule déclaration.
Q9
Que se passe-t-il si on exécute terraform destroy sans options supplémentaires ?
✅ Bonne réponse : d)
terraform destroy affiche un plan de destruction (équivalent à plan -destroy), puis demande une confirmation interactive. Une fois confirmé, toutes les ressources du state sont détruites dans l'ordre inverse de leurs dépendances. Le flag -auto-approve permet de sauter la confirmation (usage CI/CD).
Q10
Comment appelle-t-on un module dans un fichier main.tf parent ? Quelle syntaxe est correcte ?
✅ Bonne réponse : c)
La syntaxe HCL pour appeler un module est module "<nom_logique>" { source = "..." ... }. L'argument source est obligatoire. Tous les autres arguments sont les variables d'entrée du module. On voit cette syntaxe dans jour2/main.tf avec module "config_dev" et module "config_prod".
Q11
Quelle syntaxe permet d'accéder à l'output config_path du module config_dev ?
✅ Bonne réponse : a)
Les outputs d'un module sont accessibles avec module.<nom>.<output>. C'est ce qu'on voit dans jour2/main.tf : value = module.config_dev.config_path. Le préfixe module. est obligatoire pour distinguer les références aux modules des références aux ressources directes.
Q12
Que fait la fonction templatefile(path, vars) ?
✅ Bonne réponse : d)
templatefile est une fonction Terraform (pas une ressource) qui lit le fichier au chemin indiqué et retourne une string avec toutes les variables remplacées. On l'utilise dans l'attribut content d'une ressource local_file pour écrire le résultat sur le disque. Voir le module config-generator du projet.
b) est le comportement de la ressource local_file, pas de la fonction templatefile elle-même.
Q13
Quelle est la différence principale entre un workspace Terraform et un module ?
✅ Bonne réponse : b)
Un workspace (terraform workspace new dev) garde le même code HCL mais isole l'état dans un state file séparé. Un module est un répertoire de fichiers .tf réutilisable : c'est un mécanisme de factorisation du code, pas de l'état. Le projet illustre les deux : dossier jour2 workspace pour les workspaces, modules/config-generator pour les modules.
Q14
Que fait le méta-argument depends_on dans une ressource ?
✅ Bonne réponse : c)
depends_on force une dépendance explicite quand Terraform ne peut pas l'inférer automatiquement. Dans le tp-final, depends_on = [local_file.server_info] garantit que les fichiers serveur existent avant que l'inventaire Ansible soit généré, même si aucune valeur n'est partagée entre les deux ressources.
Q15
Quelle commande liste les workspaces existants et identifie celui qui est actif ?
✅ Bonne réponse : d)
terraform workspace list affiche tous les workspaces et préfixe celui actif d'un astérisque (* dev). terraform workspace show (c) n'affiche que le nom du workspace courant, sans lister les autres. terraform state list (a) liste les ressources dans le state, pas les workspaces.
Q16
Dans quel(s) cas est-il recommandé d'utiliser un backend distant pour le state Terraform ?
⚠️ Plusieurs réponses attendues
✅ Bonnes réponses : b), c) et d)
b) Vrai — Le backend distant est indispensable en équipe pour partager un état cohérent.
c) Vrai — Le state local peut être perdu ou corrompu. Un backend distant (avec versioning) protège contre ces accidents.
d) Vrai — Le mécanisme de lock empêche deux apply simultanés de corrompre l'état.
a) Faux — Le backend distant n'améliore pas la vitesse ; il peut même alourdir légèrement l'exécution (latence réseau).
Q17
Que contient le fichier .terraform.lock.hcl et pourquoi doit-il être commité dans Git ?
✅ Bonne réponse : a)
.terraform.lock.hcl enregistre les versions exactes et les hashes de vérification des providers téléchargés lors du terraform init. Le commiter dans Git garantit que tous les membres utilisent exactement les mêmes versions, évitant les divergences. À l'inverse, terraform.tfstate ne doit généralement PAS être commité car il contient des données sensibles.
Q18
Quelle fonction Terraform permet d'encoder un objet en JSON dans un fichier de configuration ?
✅ Bonne réponse : b)
jsonencode() est la fonction built-in Terraform qui sérialise un objet HCL en chaîne JSON. On la voit dans le tp-final : content = jsonencode({ id = "server-${count.index}", ip = "...", ... }). Son inverse est jsondecode(). Les noms to_json, json_encode, encode.json n'existent pas en HCL.
Q19
En Terraform, qu'est-ce qu'un provider ?
✅ Bonne réponse : c)
Un provider est un plugin Go qui fait le pont entre Terraform et une API externe. Il expose des types de ressources (aws_instance, local_file…) et des data sources, et implémente les opérations CRUD correspondantes. Dans le projet, on utilise le provider hashicorp/local — équivalent simplifié de ce que serait hashicorp/aws sur un vrai cloud.
Q20
Dans la chaîne Terraform → Ansible, quel est l'intérêt de générer l'inventaire Ansible depuis Terraform (comme dans le tp-final) ?
⚠️ Plusieurs réponses attendues
✅ Bonnes réponses : b), c) et d)
b) Vrai — Terraform connaît exactement les ressources créées et écrit un inventaire précis, sans risque d'erreur humaine.
c) Vrai — Si on augmente instance_count et relance apply, l'inventaire est régénéré automatiquement avec les nouvelles IPs.
d) Vrai — C'est le cœur de la philosophie IaC : source de vérité unique, chaîne d'outils cohérente de bout en bout.
a) Faux — Terraform gère le provisionning, Ansible la configuration logicielle. Ce sont des rôles complémentaires, pas substituables.
